# prompt-optimizer

面向 Claude Code 与 Codex 的通用提示词评测与持续优化 Skill。

它不是只把提示词“润色一遍”，而是把提示词当作可测试、可回归、可审计的程序：先建立可信基线，再通过覆盖用例、失败归因、单根因修改和同口径回归，持续寻找可验证的改进。

当前版本：`1.4.11`

## 它解决什么问题

提示词优化失败，通常不只是“措辞写得不好”。常见原因还包括：

- 评测用例或人工标签本身错误，却被当成模型错误。
- 小范围问题集提升，但相邻正确样本或全量结果退化。
- 不同模型厂商、思考模式和任务类型使用了同一种提示词结构。
- 分类、提槽和固定 JSON 本可程序判断，却引入主观 Judge 波动。
- 工具调用把“立即调用”“允许澄清后调用”和“最终调用”混为同一口径。
- 多轮运行的提示词、模型、工具、用例或评分器已经变化，分数却仍被直接比较。
- 优化只执行固定几轮，失败后停止，或者用没有依据的统一百分比决定接受与回退。

`prompt-optimizer` 将这些问题拆成独立契约和门禁，让最终结论能够回答：改了什么、为什么改、修复了哪些错误、是否误伤既有能力，以及结果对应哪一版模型和用例。

## 适用场景

| 提示词类型 | 典型任务 | 推荐评分方式 |
|---|---|---|
| 分类与打标 | 意图分类、通话标签、路由、状态判断 | `expected` 程序确定性评分 |
| 提槽与结构化抽取 | 字段提取、槽位填充、固定 JSON | `expected`，可增加字段级指标 |
| 工具调用 Agent | Function Call、工具选择、顺序与参数 | `tool-binary` |
| 普通对话 | 客服话术、多轮业务流程、角色行为 | `judge` 或任务级规则 |
| 自由文本生成 | 总结、改写、RAG 回答、内容生成 | `expected-semantic` 或 `judge` |
| 评测与模拟角色 | Judge、模拟用户、slotfiller、generate | 按目标角色和任务类型适配 |

它适合需要持续优化、可复现验证或生产回归的任务。仅想临时改写一小段文案、且不准备建立评测口径时，可以直接修改提示词，不必启动完整流程。

## 核心能力

- **覆盖驱动的用例设计**：由业务契约、状态转换、风险和正反边界决定用例，而不是预设固定总数。
- **任务级动态分类**：分类维度、等级数量、影响定义和稳定性标签由当前任务生成并经用户确认，不套固定严重度或难度模板。
- **模型可见证据校验**：期望结果依赖的事实必须真实出现在 system、用户消息、变量或工具返回中；测试说明不能冒充模型输入。
- **期望值来源优先级**：输入材料、业务字段、嵌入标签和人工标签冲突时，显式绑定权威来源和证据。
- **多种评分协议**：支持程序确定性评分、语义期望对照、维度 Judge 和工具调用 0/100 二值评分。
- **工具调用专项验证**：检查函数名、次数、顺序、时机和参数；精确契约由程序判断，仅显式语义字段调用 Judge。
- **失败归因**：区分模型失败、用例错误、装置错误、评分器错误、需求歧义和工具契约错误。
- **人工审核闭环**：用例修正必须先生成提案，由用户确认后写入；修正后强制重建基线。
- **单根因持续迭代**：一轮只验证一个根因，搭配问题集、相邻保护集、重复运行和全量回归。
- **新增需求整合门禁**：先查找已有权威规则和共享决策维度，优先合并或泛化替换；只有无法合并时才新增局部规则，避免提示词持续膨胀。
- **模型与任务适配**：按模型族、思考模式、目标角色和任务类型给出建议；只有用户接受的建议才成为硬约束。
- **能力保留与版本决策**：防止候选提示词在精简或重构时静默删除原有能力，不按最大文件编号猜测最终版本。
- **可复现运行**：通过 manifest、SHA-256、模型快照、用例快照、评分目录和决策日志还原每轮结果。
- **持久化优化记忆**：每次实际提示词改动创建新的 `prompt_vN.md`，尝试方向和结论追加到实验账本，并生成可恢复的 `OPTIMIZATION_SUMMARY.md`。
- **受控报告生成**：失败候选只记录摘要并继续优化；候选成功或用户明确要求时才生成正式报告。

## 工作原理

```text
确认任务、生产模型和成功标准
              ↓
建立能力清单、覆盖计划和同口径基线
              ↓
生成并审核正反用例 → 分层自检 → 执行与评分
              ↓
逐条失败归因
      ┌───────┴────────┐
      ↓                ↓
  用例/装置问题      真实模型问题
      ↓                ↓
人工审核、修正      定位最早分歧与单变量消融
      ↓                ↓
重建完整基线        单根因最小修改
                       ↓
              问题集 + 相邻保护集重复验证
                       ↓
                 同口径全量回归
                       ↓
          任务级接受策略通过？
             ┌─────────┴─────────┐
             ↓                   ↓
          接受版本          回退并继续其他根因
```

优化总轮数不由固定数字决定。只要仍有新的证据、可测试假设或可行动根因，流程就继续；只有达到任务成功标准、用户停止、明确资源预算耗尽或确无可验证路径时才结束。

## 角色与边界

**宿主 Agent 是优化执行者。** 当前 Claude Code 或 Codex 负责读取证据、判断根因、修改目标提示词、选择版本和组织回归。

配置中的模型只承担被明确分配的运行角色：

- `candidate`：运行被优化提示词。
- `generate`：生成测试用例。
- `simulator`：在需要时模拟下一条用户消息。
- `slotfiller`：在 text-protocol 模式下抽取工具参数。
- `judge`：只处理无法可靠程序化的语义判断。

分类、提槽、固定 JSON 和结构化抽取默认不需要结果评分模型。模型画像负责向宿主 Agent 提供适配建议，不会把“修改提示词”的职责转交给 candidate 或 Judge。

## 与常见方案的设计差异

下表比较的是常见工具侧重与本 Skill 的设计取向，不是针对具体竞品的跑分结论。

| 维度 | 常见提示词改写或评测方式 | prompt-optimizer |
|---|---|---|
| 优化单位 | 一次性改写整份提示词 | 按根因持续产生候选并验证 |
| 失败解释 | 默认归因于提示词或模型 | 先区分模型、用例、装置、评分器和工具契约 |
| 用例规模 | 固定条数或每类固定数量 | 根据覆盖项、正反边界和风险决定 |
| 接受标准 | 固定轮数、统一分数或统一修复率 | 使用任务级接受策略和用户确认的关键用例 |
| 回归保护 | 只重跑失败样本 | 问题集、相邻保护集、重复验证和全量回归 |
| 固定结果任务 | 仍由大模型主观评分 | 优先使用程序确定性评分，Judge 调用为 0 |
| 工具调用 | 只看是否调用或最终是否成功 | 检查名称、次数、顺序、时机、参数和终态 |
| 模型适配 | 一套写法用于所有厂商和任务 | 模型通用规则、任务规则和模型×任务规则分层 |
| 能力保留 | 重写后依赖人工浏览 | 能力清单和候选证据共同守门 |
| 用例修正 | 自动改标签或直接删除争议样本 | 人工审核、哈希绑定、排除登记和基线重建 |
| 可复现性 | 主要依赖聊天记录 | manifest、模型配置、文件哈希和运行范围快照 |
| 报告节奏 | 每轮输出完整报告 | 失败轮简要总结并继续，成功或用户要求时出报告 |

真正的优势不来自规则数量，而来自减少错误优化：不拿错误用例训练提示词、不把装置异常记成模型失败，也不让局部提升掩盖全量退化。

## 评分方式

| 模式 | 用途 | 是否需要 Judge |
|---|---|---|
| `expected` | 分类、提槽、固定 JSON、结构化抽取的精确结果 | 否 |
| `expected-semantic` | 同义表达、自由文本重排或业务语义容差 | 是 |
| `judge` | 多维度主观质量评分 | 是 |
| `tool-binary` | 工具名称、次数、顺序、时机和参数，每条 0 或 100 | 精确契约不需要；语义参数按需使用 |

所有模式统一输出 `totalScore`、`verdict` 和 `scoreMode`。工具二值评分同时保留 `score`、`correctCount` 和 `wrongCount`。

## 快速开始

### 1. 准备环境

需要：

- Claude Code 或 Codex。
- Python 3；内置脚本只使用标准库。
- 实际执行阶段所需的 OpenAI 兼容模型 API。

复制 `config.example.json` 为项目配置，并按实际环境填写模型、地址、密钥环境变量、厂商、模型族和能力。示例中的 `YOUR_*` 不能直接运行。

### 2. 发起新任务

可以直接对 Claude Code 或 Codex 说：

```text
使用 prompt-optimizer 优化这个分类提示词。生产模型是 Qwen 非思考模式，
工作区放在 D:/prompt-runs/classifier，先确认任务口径和配置再执行。
```

Codex 也可以显式调用：

```text
$prompt-optimizer 评测并持续优化这个工具调用提示词。
```

Skill 会识别为“新建任务”，集中确认提示词来源、生产模型、任务类型、评分方式、资源预算、成功标准和通用优化原则。

### 3. 继续已有任务

```text
继续上次的提示词优化任务，读取现有 manifest，从未通过的根因继续。
```

Skill 会读取已有 `run_manifest.json`、任务、配置、约束和版本决策，只确认发生变化的项目，不要求重复填写整套参数。

### 4. 查看结果

成功时会给出：

- 最终接受的提示词和工具版本。
- 基线与最终版本的同口径证据。
- 已修复、仍失败和发生退化的用例。
- 模型画像、硬约束和验证状态。
- 用户要求或正式接受后生成的 Markdown/HTML 报告。

失败候选不会被包装成最终成果；系统会回退、记录原因，并在仍有可验证方向时继续优化。

## 产物与可复现性

每个项目拥有自己的运行副本和数据，不直接把业务规则写回通用 Skill。典型结构：

```text
workspace/
├── config.json
├── .skill-source.json
├── bin/、prompts/、profiles/
├── reports/<task>/<run>/
└── tasks/<task>/
    ├── task.json
    ├── cases/
    └── runs/<run>/
        ├── prompt_vN.md
        ├── tools_vN.json
        ├── run_manifest.json
        ├── rounds.json
        ├── optimization-state.json
        ├── OPTIMIZATION_SUMMARY.md
        ├── trajectories-*/
        └── scores/*/
```

`run_manifest.json` 记录或关联：

- 提示词、工具定义、用例快照及 SHA-256。
- candidate 模型、生产模式、关键参数和模型画像。
- 全量、问题集、稳定性或候选验证等运行范围。
- 轨迹目录、评分目录、评分器版本和 Judge 调用量。
- 用例修正收据、约束验证、最终版本和决策日志。

因此不同模型、不同用例集、不同生产模式或修正前后的基线不会被默认为同一统计口径。

## 使用边界

- 结果可信度取决于任务定义、权威标签和用例覆盖；Skill 会帮助检查这些契约，但不能替代业务负责人确认口径。
- 模型画像是适配建议，不是厂商承诺；真实生产配置下的同集回归证据优先。
- 当模型本身缺少任务所需能力时，继续堆叠提示词规则可能不会改善结果，应根据证据停止或更换方案。
- 主观生成任务仍可能受 Judge 稳定性影响，需要任务级阈值、重复评分和人工抽查。
- 测试环境与生产环境的模型版本、思考模式、工具 Schema 或上下文不同，原有结论需要重新建立基线。
- 本地哈希链用于发现文件变化、串轮和漏审，不提供操作系统级身份认证。
- 完整流程会产生模型调用成本；先验证问题集和相邻保护集，再进入全量回归。

## 安装与管理

当前使用 CC Switch 作为唯一主存储：

```text
~/.cc-switch/skills/prompt-optimizer/
```

Claude Code 与 Codex 使用指向该目录的链接：

```text
~/.claude/skills/prompt-optimizer/  # Claude Code
~/.codex/skills/prompt-optimizer/   # Codex
```

不要维护多份实体副本，也不要直接编辑链接目录。更新主版本后由 CC Switch 统一分发。

## 项目运行副本

`bin/`、`prompts/`、`profiles/`、`templates/` 是通用基线。初始化任务时将它们复制到项目工作区，项目后续可以独立调整；`.skill-source.json` 记录来源版本。

升级 Skill 时先比较通用基线与项目副本差异，再决定同步哪些文件。项目中的 `tasks/`、`reports/`、业务配置和专项脚本不应被通用升级覆盖。

## 核心脚本

| 脚本 | 用途 |
|---|---|
| `gen_cases.py` | 按覆盖计划生成并校验用例契约 |
| `case_taxonomy.py` | 校验任务级动态用例分类体系和分类取值 |
| `runner.py` | 执行用例、工具 Mock、分层自检和运行清单 |
| `scorer.py` | Judge、确定性结果和语义期望评分 |
| `score_tool_binary.py` | 工具调用 0/100 二值评分 |
| `failure_triage.py` | 校验失败归因，只允许真实模型失败进入问题集 |
| `case_correction_guard.py` | 应用人工批准的用例修正并要求重建基线 |
| `iteration_guard.py` | 校验单根因计划、重复证据和全量接受条件 |
| `workflow_policy.py` | 校验覆盖、任务级接受策略和持续优化状态 |
| `capability_guard.py` | 防止候选提示词未经授权丢失既有能力 |
| `baseline_guard.py` | 在同模型、同用例集、同生产模式下选择基线 |
| `compare_rounds.py` | 生成同集或显式子集的轮次对比证据 |
| `optimization_journal.py` | 创建候选版本、追加尝试结论、记录里程碑并生成恢复摘要 |
| `report_gen.py` | 按 manifest 或显式选择生成报告 |

运行参数以各脚本的 `--help` 和以下参考契约为准，README 不重复完整 CLI 手册。
